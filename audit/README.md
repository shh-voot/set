## 复核方式

### A. 不安装科学计算依赖：检查附件完整性

在仓库根目录，使用 Python 3.10 或以上版本：

```shell
python audit/review.py verify
```

`MANIFEST.json` 记录所有公开审计附件的 SHA256。审计目录的 `.gitattributes` 固定按原字节保存，避免 Windows/Linux 行尾自动转换改变哈希。该命令验证文件是否与交接包一致，**不替代数学或程序复核**。

### B. 建立独立 Conda 环境

```shell
conda create -n set-audit python=3.10 pip -y
conda run -n set-audit python -m pip install -r audit/requirements.txt
```

不向团队现有开发环境安装依赖。这里固定复核环境版本以便比较；不是建议业务程序永久使用这些版本。所列 pip 依赖来自第二轮实际审计环境。

### C. 独立重放检查

```shell
conda run -n set-audit python audit/review.py run --round all
```

此命令按两个完整 Git 提交 ID 导出受审查数据及源码，在新建副本中重算交付表的约束检查。只核第二轮可用 `--round 2`。

还需要运行原四问求解流程、ALNS 实验及新实验反例时：

```shell
conda run -n set-audit python audit/review.py run --round all --full
```

每次运行都创建 `audit/.runs/<唯一编号>/`，其中包含快照、求解输出、日志及 `run_summary.json`。该目录已忽略，不会写回正式 `结果/`、`解题-gpt/结果/` 或已发布证据。入口使用 `git archive`，不会切换分支、重置、stash 或改写 Git 历史。

**运行成功表示复核到了记录中的问题，不表示解题方案通过验收。** 例如第二轮必须再查出 3 条交付超载、23/25 箱迟到，才符合这次版本复核的预期。

完整复核需要本地 Git 中含两个历史提交；浅克隆如缺历史，应先 `git fetch --unshallow`。完整依赖与日志较多，建议在正常克隆中执行。无需打开 Word、安装 MathType 或接入其他成员环境。

## 证据与来源约定

- [问题机器清单](issues.json) 与 [合并问题清单](ISSUES.md) 使用相同编号 `AUD-01` 等。讨论或修复提交可引用该编号。
- 每轮 `evidence/` 保存原题含公式文本、单元格提取、逐架次/逐箱 CSV、检查摘要、复现结果及运行日志。Word 数学内容来自文档 XML；并非只依靠普通文本复制。
- 代码引用链接固定到被审查 Git 提交；因此后续代码修复不会使历史证据位置漂移。包内附件使用相对链接，可在 GitHub 与本地浏览。
- `reference_*` 是明示工程假设对照，**不是声称找到了原题缺失的唯一能耗公式**。Q3 超载行超出航程定义域，其外推能耗不得作为合规答案。
- `code_*` / 原表 `feasible`、`on_time` 只表示程序复算或原交付字段，不等于独立审计通过。
- CP-SAT 的 1.09 min 案例是合成反例；4 个断连点、Q3 超载及 Q4 迟到则来自实际交付数据。
- 原题、论文 PDF、DEM 等已在仓库及历史提交中。本包不重复提交大型输入图片、Conda 环境和复制求解目录；可由固定提交重建。
- `pull_preflight.json`、`integrity_check.json` 是当时审查阶段的历史校验记录。发布整理只调整了报告链接和复核说明；公开包以 `MANIFEST.json` 校验，不能拿历史本机审计目录的哈希当作发布包哈希。
